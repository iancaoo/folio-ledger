# 部署、备份与恢复

适用版本：NocoBase 2.2.24、Finance 插件 0.1.0、Node.js 24.19.0、PostgreSQL 17.9。已验证环境为 macOS arm64、本机独立 PostgreSQL 和本地文件存储。Linux 生产主机、外网访问、SSO、多实例及对象存储未经过本次验收。

第一阶段技术验收见[验收记录](第一阶段验收记录.md)。本地版本可供模拟试用；正式数据录入还需关闭[业务待确认项](试用与业务确认.md)。

## 1 本地安装和启动

解压发布包到新的项目目录，安装 Node.js 24、PostgreSQL 17 命令行工具和 Python 3。执行：

```sh
python3 scripts/setup-local.py
```

安装使用锁文件，不重置已有数据库。已存在的环境只迁移；平台代码保持 2.2.24。访问 `http://127.0.0.1:13000/admin/finance`，凭据在 `.runtime/dev-credentials.json`，权限为 600。

启动和停止见 [README](../README.md)。`setup-local.py`、`dev-database.py` 和 `dev-app.py` 只用于本机演示，不用它们接管已有生产数据库。

## 2 多人部署前需要完成的配置

由部署管理员提供主机、域名、HTTPS、数据库账号及持久卷。保持单个 NocoBase 应用和单个 PostgreSQL；本版不需要 Redis 或额外队列。

| 配置 | 部署要求 |
| --- | --- |
| 依赖和程序 | 在目标机器按 `apps/nocobase/yarn.lock` 安装；重新构建 Finance 插件；不复制开发机 `node_modules` |
| `APP_KEY` | 使用独立随机值，长期保留；恢复时必须使用与备份配套的值 |
| `STORAGE_PATH` | 独立持久目录，保留 `finance`、`uploads`、`apps`；不放入代码发布覆盖范围 |
| 数据库 | PostgreSQL 17；独立库和应用账号；普通业务用户不直接连接 |
| `FINANCE_DEMO_MODE` | 正式环境设为 `false`；先由配置管理员确认候选项和产品组成员 |
| 请求体 | `REQUEST_BODY_LIMIT=16mb`；HTTPS 代理也允许相应大小，以容纳 10 MB 文件的 Base64 |
| 网络 | 应用监听本机或私网，用户通过 HTTPS 访问；数据库不对业务用户开放 |
| 账号 | 分配 `finance_editor`、`finance_reader`、`finance_configurator`；产品组另加 `finance_product`；日常录入不使用平台 root |
| 日志 | 限制读取权限；日志、数据库、原文件、草稿及备份不进入公开代码仓库 |

安装顺序为：准备私密 `.env` → 安装锁定依赖 → 构建插件 → 空库执行 `nocobase install --lang zh-CN` → 启动应用 → 检查菜单、角色及一条模拟录入。已有库执行升级，不执行强制安装或清库。

本次未连接生产服务器。部署管理员应在目标环境重复 A26、A27、A31、A34、A36、A38、A39、A42，并按真实访问网络核对性能。需要新增商业插件、SSO 或外部存储时，应先确认范围和成本。

## 3 离线配套备份

`scripts/backup.py` 同时保存整库逻辑备份、本地文件清单和 SHA-256。数据库包含平台页面、角色、用户、迁移、候选配置、业务数据、草稿、来源和请求凭据。

数据备份与密钥分开存放：

| 目录 | 内容 |
| --- | --- |
| 数据备份目录 | `database.dump`、`storage/finance`、`storage/uploads`、版本和源代码摘要、文件清单 |
| 独立密钥目录 | `runtime.json` 中的 `APP_KEY`、`apps` 中的平台 AES 密钥、配套备份 ID 和私密校验清单 |

两个目录都必须受控。文件清单不会写出密钥、数据库密码或登录密码，但数据库备份本身仍包含敏感业务数据和账号资料。SHA-256 用于检查完整性，不提供加密或签名；正式环境应使用受控且加密的备份介质。

在 `.runtime` 下准备权限为 600 的 JSON 配置文件。以下是结构示例，值由环境管理员填写，不把实际文件提交到 Git：

```json
{
  "database": {
    "host": "127.0.0.1",
    "port": 15432,
    "name": "finance_dev",
    "user": "finance_app",
    "password": "填写当前数据库密码"
  },
  "storage_path": "/项目绝对路径/apps/nocobase/storage",
  "app_port": 13000,
  "app_key": "填写当前环境的 APP_KEY",
  "stop_command": ["python3", "scripts/dev-app.py", "stop"],
  "start_command": ["python3", "scripts/dev-app.py", "start"]
}
```

命令数组为本机示例。生产环境应改为管理该服务的明确命令，停止全部应用实例、后台任务和其他写入者。若应用已由维护流程停止，可同时省略两个命令。脚本检查应用端口和数据库其他连接；仍有连接时拒绝备份。其他维护客户端也应断开。

```sh
chmod 600 .runtime/backup-profile.json
python3 scripts/backup.py create \
  --profile .runtime/backup-profile.json \
  --backup .runtime/backups/20261014-01 \
  --secrets .runtime/backup-secrets/20261014-01

python3 scripts/backup.py verify \
  --backup .runtime/backups/20261014-01 \
  --secrets .runtime/backup-secrets/20261014-01
```

每次使用新目录。成功清单最后写入；无完整清单不能当作成功备份。服务由脚本停止时，备份完成或失败都会尝试重新启动。脚本不删除旧备份，不设置后台调度。

当前备份仅支持本项目单应用、PostgreSQL 和 `finance/uploads` 本地存储。检测到其他存储类型或范围外的文件根目录时会拒绝执行；先扩展备份方案，再启用这些配置。平台运行缓存、日志和 `node_modules` 不属于恢复数据；代码、锁文件及插件从配套发布物取得。

## 4 恢复到隔离环境

1. 准备与备份一致的发布物。脚本核对平台包、锁文件、插件源代码、迁移及字段定义摘要。准备新的空数据库、不同端口和新的存储目录；不要启动应用。
2. 创建目标配置文件，填写目标库和目录，不写源环境的停止／启动命令。目标数据库必须为空，且库名不能与源库相同。
3. 执行恢复。脚本先校验数据及密钥目录，再用 `pg_restore --single-transaction` 恢复整库，并复制文件和平台密钥。已有数据库和持久目录不会被覆盖。

```sh
python3 scripts/backup.py restore \
  --profile .runtime/restore-profile.json \
  --backup .runtime/backups/20261014-01 \
  --secrets .runtime/backup-secrets/20261014-01
```

4. 从独立密钥目录的 `runtime.json` 将配套 `APP_KEY` 配入目标环境。使用目标数据库、存储和端口启动；不要沿用源环境连接地址。恢复脚本不自动启动应用。
5. 核对表和约束、用户与角色、菜单、候选配置、版本数、70 份模拟持仓、文档下载和请求重试。等待任务恢复，检查解析、上传和删除状态。记录结果后才能切换访问入口。

数据库恢复和文件复制不是一个跨介质事务。复制失败时保持目标应用停止，检查原因后用新的空目标重新恢复。不要在缺文件的恢复环境继续录入，也不要通过清空正式库来重试。

同机隔离演练已验证 28 个表的内容摘要和行数、90 条约束、账号与权限、AES 密钥、原文件、草稿、成功凭据及四种中断状态。见[恢复证据](verification/M5备份恢复验证.json)。生产主机和异地备份副本应分别演练，不能以本机通过替代。

## 5 升级与回退

升级顺序：配套备份 → 在隔离恢复副本中升级和回归 → 停止正式写入 → 部署固定版本 → 迁移 → 启动和冒烟检查。

```sh
node .runtime/tooling/node_modules/yarn/bin/yarn.js --cwd apps/nocobase build @finance/plugin-core
node .runtime/tooling/node_modules/yarn/bin/yarn.js --cwd apps/nocobase nocobase upgrade --skip-code-update
```

第二条只运行迁移，不自动更新平台依赖。不要把未验证的 NocoBase 新版本混入业务插件发布。当前证明的是 2.2.24 下的空库安装、重放、已有数据迁移和恢复；没有声称通过跨大版本升级。

升级解析规则后，旧的未完成批次可能要求下载原件后新建批次；原始内容和纠错记录保留。已经完成的批次仍返回原结果。

存在不兼容迁移时，回退必须恢复配套数据库、文件和密钥，并使用旧发布物；只切换前端或插件代码不足以回退数据。

## 6 保留周期与日常运行

| 对象 | 当前行为 | 部署时建议 |
| --- | --- | --- |
| 未关联的文档暂存 | 默认 168 小时清理；可用 `FINANCE_STAGED_FILE_RETENTION_HOURS` 调整 | 初期保留七天，至少一小时 |
| 孤立导入原件与 `.part` 残片 | 默认 168 小时；`FINANCE_IMPORT_ORPHAN_RETENTION_HOURS` | 只清理无关联原件及暂存残片，不删除已关联批次 |
| 已关联原件、导入行与纠错 | 保留；没有自动删历史的动作 | 由业务确认保留期，再设计受控归档 |
| 草稿 | 本人删除或正式保存时移除 | 不跟随上传暂存清理 |
| 请求凭据、来源及版本 | 保留 | 不独立清空，以免破坏重试或来源核对 |
| 日常备份 | 已提供工具，未启用生产调度 | 每日一次，升级前另做一次；建议日备份 30 份、月备份 12 份，待管理员确认 |
| 密钥及备份介质 | 分开受控保存 | 密钥与对应备份同寿命；验证异地副本可恢复 |

生产调度应执行维护窗口中的备份命令，失败时通知维护者。当前尚未启用定时服务或自动删除旧备份。建议每月抽查恢复，升级前必须演练。

性能基准：本机 Apple M4 Pro、48 GiB、十万笔交易、三十万条净值、五会话。交易列表 P95 71ms，主体持仓 13ms，交易保存 30ms；五份一万行预览最慢 9.172 秒。浏览器列表刷新 P95 102—156ms；首次打开整个应用约 2.649 秒，单独记录，不计入页面内列表加载目标。完整方法和样本见[性能证据](verification/M5性能验证.json)。
